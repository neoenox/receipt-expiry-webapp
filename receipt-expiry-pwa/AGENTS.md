# このリポジトリの作業ルール

## デプロイと CI

- PR を作る前に `.github/workflows/ci.yml` を読む。参照しているディレクトリと env が今の構成と合っているか確認する。
- CI が失敗したら、推測でコードを触らず、まず `gh run view <run-id> --log-failed` で失敗箇所を特定する。
- `main` は保護ブランチなので直接 push しない。PR を作って CI を通してからマージする。
- rebase した後は CI が再実行されるので、マージ前に再度完了を確認する。

## 見た目の変更

- CSS や DOM を触ったら、数値やコードだけで確認済みにしない。目視テスターに実画面を見せて確認する。
- `width: 100%` や `min-height` のような親ルールが子要素に効いていないか確認する。幅だけ直って高さが残ることがある。
- PC 幅（1280x800）とスマホ幅（375x812）の両方で見え方を確認する。

## 本番反映の報告

- 「本番に反映されているか」を聞かれたら、`git status` だけで答えない。
- `git status` と `gh run list --branch main` の両方を見て、未コミットの変更がないか、main の CI とデプロイが成功しているかを確認してから答える。
- リポジトリ内に設定ファイルが無くても、GitHub 側で Git 連携が設定されている場合は自動デプロイされる。リポジトリだけを見て「自動デプロイではない」と決めつけない。

## 設定不足による機能制限

- 秘密情報が GitHub secret に無い場合は、エージェント側で推測して生成しない。必要な secret 名をユーザーに伝える。
- 現状、通知の本番到達には `VAPID_PRIVATE_KEY` と `VAPID_PUBLIC_KEY` の GitHub secret が必要。これらが無い場合、通知は届かない。
